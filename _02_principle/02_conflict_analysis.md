## 一、冲突清单与裁决

### C-A【裁定级】hs-project-skill 五段签名 vs 框架层统一签名

| | 内容 |
|---|---|
| 冲突点 | SOP 强制 `boolean method(input, output, context, metrics, evolution)`；`框架设计 §一-5`/`框架详细设计 §3.1` 定义 `boolean step(input, output, context, tenant, metrics)`（五参全 map，无 evolution，多 tenant） |
| 性质 | 方法签名形态冲突：evolution（反馈与优化，方法结束前必须回填）在框架签名中缺席；tenant 的位置两说 |
| 证据 | hs-project-skill SKILL.md / method-spec.md §一-二；business/框架层_开源/1_框架设计.md §一-5、2_框架详细设计.md §3.1 |
| 裁决 | **按 SOP 冲突裁决顺序（用户当场指令=按 SOP 重排 > SOP > 其他）采用 SOP 五段签名**：① `tenant` 移入 `context`——框架 LLD §九本就以 contextvar 承载 `TenantCtx(tenant_id, domain_id, actor, trace_id)` 并随上下文贯穿，独立参数本就冗余；② `evolution` 补入第五段，并与框架异常策略引擎对接：业务方法以 `raise Undecidable(reason_code)` / evolution 回填表达失败语义，policy 引擎按错误类型路由（Undecidable→abstain 挂复核队列，A15 语义完整保留） |
| 落点 | `_03/ADR-001`；代码 `metamemory/src/metamemory_framework/container/types.py + signature.py + policy.py`；_07 全部方法按五段登记 |

### C-F【口径收敛】Memory API 动词面三种表述

| | 内容 |
|---|---|
| 冲突点 | 02 §八与核心层功能实现 §二："Memory API（add/search/context/manage 四动词）"；Mem0 对比 §三："add / search / get+history / delete（update 经 manage）"；同档 §三-③："manage 一个动词承载四类语义过重，**拆 correct/visibility/authz/forget 四个显式子动词**" |
| 裁决 | 三者非矛盾而是精度递进，统一为：**核心动词 = add / search / context（可选）/ manage（子动作 = correct / visibility / authz / forget）**；`get+history` 为读取面（GET /memories/{id} 及其 /history），`delete` 语义并入 `manage.forget`（灰/硬双轨）。以 _06 接口清单为唯一权威 |
| 状态 | 已收敛（_06/01_external_api.md） |
