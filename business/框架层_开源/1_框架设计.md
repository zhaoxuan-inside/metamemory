## 一、设计思想（六条公设）

| # | 公设 | 架构含义 |
|---|---|---|
| 1 | 长程任务（秒级到分钟级）是常态 | 请求**任务式**：同步受理（落袋 + task_id），异步流程图执行，进度经 SSE/Webhook 回传 |
| 2 | 资源**优先保证已进入任务的完成** | 准入控制 + 背压：有界队列，水位以上拒绝新任务；内部重试优先于新任务准入 |
| 3 | 流程**局部并行、整体受控** | 流水线 + 图执行：节点间按边推进，节点内 fan-out 并行，跨任务按节点流水线并行 |
| 4 | 全模块**无状态** | 状态只在持久层；worker 可随时扩缩容重启；节点幂等（at-least-once） |
| 5 | 所有方法**抽象为可编排单元** | 步骤 = 统一签名 `boolean step(input, output, context, tenant, metrics)`，注册进框架，由引擎派发 |
| 6 | **框架不含业务** | 框架只认识步骤/流程图/契约/异常策略/优先级/指标；业务 = 注册步骤 + 声明流程图（数据），零框架改动接入 |

## 二、总体架构（两层视图）

```
┌──────────────────────── 业务层（接入方，扩展点）────────────────────────┐
│ ① 步骤实现库：处理容器语义的原子方法（注册进框架步骤注册表）                │
│ ② 流程定义：声明式流程图（数据，版本化——顺序/分支/循环/汇合/等待/子流程）    │
│ ③ 同步读路径：交互式低延迟逻辑（挂 api 单元，不走任务系统）                 │
│ ④ 状态机：强一致短事务（DB 约束兜底），下游动作以事件入队                   │
│ ⑤ 契约与异常策略配置：字段映射、拍平映射、错误路由                        │

│ ① 流程定义与执行引擎：图模型（step/fork/loop/switch/wait/subflow/join）      │
│                 · 就绪调度（SKIP LOCKED）· 检查点与游标 · 断点续跑           │
│                 · 处理容器五段执行 · 数据契约抽取 · 异常策略引擎             │

│ ② 流量组织：准入控制（水位/背压）· 多级优先队列 · 租户公平 · 熔断             │
│ ③ 推送与长连接：SSE/WS Hub（无状态）· 进度事件 · Webhook 出站                │
│ ④ 监控告警（自动，业务零代码）：节点/队列/任务指标 · OTel trace 链           │
│ ⑤ 多租户隔离：RLS 会话生命周期 · 租户上下文贯穿 · 隔离矩阵                   │
│ ⑥ 平台服务：组件接口族（9 槽位 + 防腐层）· 部署档位 · 推理双通道 · 密钥       │

   部署单元（全部无状态）：api │ worker 池（按节点资源档分级）│ scheduler │ push-hub
```

**框架职责边界（封闭集合，决策 A13）**——框架只负责九项，此外不做任何事：

| # | 职责 | 承载子系统 | 关键机制 |
|---|---|---|---|
| 1 | 注册组件容器 | 步骤注册表（component_registry） | L1 注册配置、多版本并存、注册校验 |
| 2 | 编排组件容器 | 流程图引擎 | L2 流程定义、图校验、就绪调度、分支/循环/汇合/等待/子流程 |
| 3 | 接收请求作为任务 | 受理面（API/MCP/事件） | 幂等键、同事务入队、准入背压、202 + 进度订阅 |
| 4 | 管理任务执行环境 | 任务上下文包 + 装配器 | 检查点、输入视图、调用缓存、配置快照、Store 槽位与档位 |
| 5 | 重启节点任务不中断 | 恢复协议 | 租约判死重派、活跃游标重放、幂等重放不重复付费、优雅退出——**节点可中断，任务不中断** |
| 6 | 流程监控 | 观测引擎（自动，业务零代码） | 节点/队列/任务指标、trace 链、积压与死信告警 |
| 7 | 组件容器升级 | 版本管理（§3.8） | 多版本并存、CI 合同测试 + 样本干跑、在途快照不受影响、灰度与回滚 |
| 8 | 组件配置 | data_contracts + 注册表 | L1 提取/拍平/异常策略配置化 |
| 9 | 组件编排配置 | pipelines 表 | L2 流程图声明、节点级覆写、版本化发布与回滚 |

**负空间（框架明确不做）**：不含业务语义与流程含义；不含同步读路径的业务逻辑；不含数据建模；不含权限裁决；不直接对接外部组件（经防腐层）。

**项目形态（决策 A14，v2 三层两仓）**：`metamemory-framework`（框架层，开源，零业务，语义化版本发布，Python 包 + lite 单容器镜像）与 `metamemory`（核心层，开源，import 框架——收发协议本体）两包同仓发布；业务层 `metamemory-x` **独立闭源仓库**，import 单向 x → core → framework。框架表随框架包迁移；核心表随核心包迁移。

## 三、框架核心：流程定义与执行引擎

### 3.1 流程定义（数据化流程图）

流程 = **版本化的有向图定义**（存 pipelines 表，数据而非代码）。节点六型 + 边两类：

| 节点类型 | 语义 | 关键属性 |
|---|---|---|
| step | 原子步骤（处理容器执行） | 步骤名、输入契约、输出映射、异常策略、资源档 |
| fork | 扇出：按表达式物化 N 个子任务并行执行后汇合 | from（列表路径）、循环体子链、join（all/quorum/any + 超时）、批大小 |
| loop | 循环：迭代执行循环体直至条件满足 | 循环体子链、until 条件表达式、max_iterations（强制上限） |
| switch | 分支：多路条件路由 | on（取值路径）、cases、default |
| wait | 等待：挂起直至外部事件或超时 | 事件名、签名校验、超时 → 按异常策略 |
| subflow | 子流程：嵌套另一条流程图（独立检查点） | 流程名 + 版本 |

边：顺序边（from → to）；**条件边**（when 条件表达式，json-logic 求值，输入 = 前驱 output map + context；不满足则不激活，全未激活走 default）。

**图约束（编译期校验，不过拒绝发布）**：① 静态图无环——循环仅经 loop 节点；② 节点引用的步骤已注册、契约映射可解析；③ 每条路径可达终态（join/wait 必有超时）；④ 任务级总闸（整图超时、节点数/深度上限）；⑤ **无静默兜底（新增，设计原理约束 15）**：switch 的 default 与条件边全未激活的兜底路径不得直接进入"成功终态"——必须显式指向弃权/复核/死信类节点（编译期校验）。

分支与循环语义：分支 = 节点完成后求值出边条件，激活边指向的节点进入就绪集（多边可同时激活 = 并行分支）；循环 = 每轮执行体后求值 until，迭代间提交检查点（崩溃从第 k 轮续跑），max_iterations 耗尽按异常策略；批处理循环 = fork 按列表物化子任务分批执行。

### 3.2 处理容器（方法的执行模型，决策 A9）

input / output / context / metrics / tenant **全部为 map**——方法本质是一个**特定的处理容器**，框架按配置五段执行：

```
① 提取：按输入映射配置，从 context 与 input 的 map 中抽取需要的信息（required/缺省/类型断言）
② 封装：将提取到的信息构造为该方法要操作的对象——强类型只在容器内存在
③ 操作：方法内部完成对象的操作——纯业务逻辑，不碰 map、不碰框架
④ 拍平：返回的对象内容按输出映射配置拍平，写入 output map（下游按契约再提取）
⑤ 异常：失败时按异常策略配置针对性处置（见 3.4）
```

边界 map 保解耦，容器内强类型保质量——业务方法零样板（只写"操作"段）。

### 3.3 数据契约（模块解耦，决策 A6）

步骤/模型间**不传对象、不 import 类型**——传递**版本化数据文档**（JSON，落 task_steps 检查点）；每个步骤用字段映射配置声明"我需要什么、从哪里取"（JSONPath），框架统一抽取；LLM prompt 输入绑定同走映射配置。上游换模型/改 schema = 改一行映射配置，下游零改动。契约进 CI：黄金样本回放 + 字段断言（合同测试），映射失效阻断发布。

### 3.4 异常策略（声明式容错，策略即数据）

| 错误类型 | 处置 |
|---|---|
| 契约校验失败 | 转复核队列，不重试 |
| 瞬态错误（超时/5xx） | 重试（次数/指数退避）——重试优先于新任务准入 |
| 外部依赖错误 | 降级（备用实现/备用路径，经防腐层声明） |
| 业务失败 | **回复指定内容**：fallback 值按输出映射写入 output map，流程可继续 |
| **不可判定（abstain，新增）** | **挂人裁**：写复核队列（pipeline_review_queue）+ 显式原因码 + 待裁状态；这是**一等合法结论**而非异常（设计原理约束 15/ADR 20）——框架要求业务注册 abstain 处置时提供原因写入路径，缺省配置视为违禁 |
| 兜底 | 死信 + 告警 |

策略声明在步骤级（默认）与节点级（覆盖）。**禁止项**：任何以"默认值兜底"代替 abstain/死信的配置（默认值 = 静默处理，违反设计原理约束 15，CI 策略完备性检查拒收）。

### 3.5 任务与检查点（断点续跑）

**任务模型**（PG 表）：tasks（流程/版本/优先级/状态/幂等键/参数/**配置版本绑定**）+ task_steps（节点/状态/attempts/租约/Join 策略/父引用/输入输出引用）。派发：就绪节点（入度满足且条件为真）经 `SKIP LOCKED` 领活；入队与业务写入同一事务（Outbox 免除）。

**检查点 = 任务游标**：节点完成即原子提交（输出文档 + 状态推进 + 后继激活同一事务）；任务游标 = 当前活跃节点集合——图执行任意时刻的恢复点。

**生命周期**：提交（受理 + 落袋 + 入队同事务）→ 实例化流程图（绑定版本）→ 就绪节点派发 → 容器执行 → 检查点提交 → 条件推进/分支/循环/汇合 → 终态。任意节点异常退出 → 租约过期 → 活跃集重放继续（客户端感知为进度暂停后续传）。

### 3.6 子任务衔接与崩溃恢复（可靠性核心）

**崩溃恢复三件套（决策 A7）**：

| 故障 | 检测 | 恢复动作 | 丢失面 |
|---|---|---|---|
| worker 崩溃/被杀 | 租约过期（心跳续期停止） | 节点重置就绪 → 重派；命中调用缓存直接续跑 | 0 |
| 节点整机宕机 | 同上 | 同上 | 0 |
| scheduler 崩溃 | leader 锁随连接释放 | 备位从 PG 状态表重建派发视图 | 0 |
| Redis 崩溃 | 连接错误 | PG 是唯一真源：队列重建，缓存冷启动 | 仅缓存命中 |
| 外部依赖故障 | 节点错误 | 退避重试 → 降级路径 | 0 |
| 子任务死信 | join 等待超时 | 父任务按 Join 策略 → PARTIAL + 复核队列 | 该子任务 |

外部**调用缓存**：llm_calls（节点/输入哈希/prompt 版本/response/cost）——幂等重放，崩溃重试不重复付费。

四条不变式：① 节点完成 = 原子提交；② 幂等重放；③ 优雅退出（SIGTERM 停领新活、释放租约）；④ 配置快照绑定。

**子任务衔接通知（决策 A8，三层通道）**：

| 通道 | 载体 | 用途 | 可靠性 |
|---|---|---|---|
| 推进通知 | PG pg_notify + **周期扫描兜底** | 子节点完成 → 推进父节点/激活后继 | 状态表是真源，NOTIFY 仅为加速 |
| 进度通知 | Redis pub/sub → SSE Hub | 客户端实时进度 | 尽力而为（轮询兜底） |
| 回调通知 | Webhook 出站（重试队列 + 签名） | 外部系统（wait 事件源等） | 至少一次 + 幂等键 |

衔接语义：串行衔接与后继激活**同事务**；fork 子任务独立租约/检查点；join 按 all/quorum/any 汇合；**防孤儿**——join/wait 必有超时，任何任务都有终态。

### 3.7 编排配置模式（业务组件容器的接线方式）

四层配置——**配置即流程，配置即接线**，业务不写编排代码：

| 层 | 配置者 | 载体 | 内容 |
|---|---|---|---|
| L1 步骤注册配置 | 业务（组件作者） | 代码内声明 + 注册表 | 容器五段映射、异常策略默认、队列/资源档/批处理/幂等键 |
| L2 流程定义配置 | 业务（流程作者） | YAML/JSON → CI 校验 → pipelines 表 | 流程图：节点 + 条件边 + fork/loop/switch/wait/subflow；节点级覆写 |
| L3 运行时装配配置 | 部署 | profile + 环境变量 | Store 槽位实现、worker 池规格、优先级与准入水位 |
| L4 实例参数 | 受理时 | tasks.params | 任务参数 + 版本绑定快照 |

覆盖方向：L2 节点级 > L1 步骤级 > 内置默认。配置校验（CI 五关）：图校验 / **配对校验**（上游输出映射字段 ⊇ 下游输入映射可解析）/ 策略完备（兜底 "*"）/ 样本干跑（外部调用 mock 验证分支与循环终止）/ 资源队列存在性。配置变更生命周期：PR → CI → 版本化发布 → 在途任务不受影响 → 回滚 = 指回旧版本。

L1 步骤注册配置示例：

```yaml
step:
  name: enrich.parse            # 全局唯一：域.动作
  version: 3
  container:
    process: adapters_enrich.ParseContainer.process  # ③ 操作段（唯一代码）
    input:                          # ① 提取映射（从 input / context map）
      payload: {path: "$.payload", required: true}
      mode:    {path: "$.meta.mode", default: "std"}
      tenant:  {from: context, path: "$.tenant"}
    output:                         # ④ 拍平映射（返回对象 → output map）
      items:  {from: "items", path: "$.items[*]"}
      status: {from: "status", path: "$.status", default: "ok"}
    error_policy:                   # ⑤ 异常策略（错误类型 → 处置）
      ContractViolation: {action: review}
      TransientError:    {action: retry, max: 3, backoff: exp}
      DependencyError:   {action: fallback, to: enrich.parse_lite}
      BusinessReject:    {action: reply, value: {status: "skipped"}}
      "*":               {action: dead_letter, alert: true}
  scheduling:
    queue: enrich
    resource: cpu
    timeout: 120s
    batch: {max_size: 32, window: 500ms}
    idempotency: {key: "{task_id}:{node_id}:{input_hash}"}
```

### 3.8 组件容器升级（版本并存与灰度，职责 7）

组件以 `name + version` 注册，**多版本并存**；流程定义可钉住版本或指向 latest——任务创建时解析并**绑定具体版本**（配置快照），在途任务永远执行绑定版本。

```
新版本实现 → 注册（version+1）→ CI 门禁（合同测试 + 黄金样本干跑）
  → 发布（新任务可见）→ 监控对比 → 旧版本 deprecated → 在途归零后退役
```

在途兼容（升级/回滚零影响）；回滚 = 指回旧版本；灰度（version hint 按租户/百分比路由）；契约破坏性变更禁止原地改——新版本 + 新契约版本。

## 四、流量组织

| 机制 | 设计 |
|---|---|
| 准入控制 | 队列水位监控；全局高水位 → 拒绝（429 + Retry-After）；**落袋类同步写永不拒绝** |
| 多级优先队列 | 交互读 > 落袋写 > 治理关键 > 流程常规 > 批量——高级别抢占 worker 配额 |
| 内部优先 | 重试与断点续跑优先于新任务准入 |
| 租户公平 | 每租户在途上限 + 加权轮转；免费/付费档差异 = 上限与优先级配置 |
| 熔断降级 | 外部依赖错误率超阈 → 熔断半开；降级路径接管（防腐层声明） |

## 五、推送与长连接

SSE/WS Hub 无状态（连接状态在 Redis pub/sub）：任务进度事件（节点推进/分支/循环轮次/完成/失败）、确认类事件、Webhook 出站共用。受理响应即含 task_id + SSE 订阅地址。

## 六、监控（非业务，自动）

业务代码**零监控代码**：装饰器 + 引擎自动产出——节点耗时/错误率/重试率、队列深度与等待、任务端到端时延与成本（按节点归因）、死信率、循环迭代与 fork 扇出分布（图执行健康度）、**abstain 弃权率与 default 路径命中率（上游质量归因必看：弃权率突升 = 前置级联失灵或输入分布漂移，设计原理约束 15 失效信号）**。OTel trace：task_id 为根、节点为 span 链（含分支路由与循环轮次）。告警：积压超水位、死信率突增、外部依赖错误率、P99 退化、**default 兜底路径进入"成功终态"（配置缺陷级告警）**。

## 七、平台服务：组件接口族 / 部署档位 / 防腐层

**组件接口族与部署档位（决策 A10）**：

| 槽位 | full 档 | lite 档（开源默认） | 缺失降级 |
|---|---|---|---|
| DataStore | PostgreSQL（RLS/SKIP LOCKED/advisory lock/JSONB） | SQLite（应用层租户过滤，单租户强制） | ——（必需） |
| VectorStore | pgvector | sqlite-vec | 内存向量 |
| FullTextStore | PG FTS + zhparser | SQLite FTS5 | ——（必需） |
| GraphStore | PG 邻接表 + CTE | SQLite 同构表 | ——（必需） |
| TaskQueue | PG SKIP LOCKED | SQLite CAS 抢占 | 内存队列 |
| CacheStore | Redis | 进程内 LRU+TTL | **Redis 缺席 = 内存缓存自动顶上** |
| LockStore | PG advisory lock | 文件锁/单实例 | 内存锁 |
| ObjectStore | MinIO | 本地文件系统 | ——（必需） |
| PubSubStore | pg_notify + Redis pub/sub | 进程内事件总线 | 扫描兜底（§3.6） |

降级矩阵语义：组件**允许缺失**，功能语义不变、性能保证降级、启动标明档位。多租户硬隔离（RLS）是 full 档能力——SQLite 档强制单租户声明。档位是槽位预设而非枚举。

**本地封装原则（防腐层，决策 A11）**：一切外部组件**不得直接接入**——必须经本地封装模块访问；业务禁止 import 外部 SDK（白名单仅限 `infra/adapters/*`）。封装层四职：协议翻译、超时/重试/熔断、缺失降级、打点脱敏。登记表：PG/SQLite → DataStore；Redis → Cache/Lock/PubSub；MinIO → ObjectStore；LiteLLM → GatewayProvider；llama.cpp/ONNX → EmbeddedProvider；嵌入/重排 → Vector/Reranker 适配器；NLP/OCR/ASR → 能力适配器；观测 → TraceSink/EvalRunner；渠道 → NotifyChannel；APISIX → 进程外部件。与数据契约（A6）对称：**入向契约化，出向封装化**。推理双通道（InferenceProvider：嵌入式 + 网关，双向降级链）属此族。

## 八、多租户隔离（基础设施层）

两个正交安全层：**租户隔离**（框架硬边界）与**可见性权限**（业务语义，读路径扩展点接入）。框架承担前者：

**隔离单元映射（A5）**：tenant = 数据主权硬边界（个人域 1:1 租户，组织实例 = 组织租户）；domain = 业务容器；account = 认证主体。子域主权 = 跨租户读被 RLS 直接拦下。

**隔离矩阵**：PG（RLS FORCE + 会话变量生命周期 + tenant_id NOT NULL 前缀索引）｜字段级 AES-GCM 按租户密钥｜MinIO prefix｜Redis key 前缀 `t{tid}:`｜任务携带 tenant_id + 上下文贯穿｜推送连接 JWT claims + audience 校验｜日志 tenant 只作标签｜LLM 按租户 tag｜备份/导出按租户。

**RLS 骨架**：`FORCE ROW LEVEL SECURITY` + 策略 = 本租户 OR 授权放行（授权表 JOIN）；跨租户关系表（授权/成员）专属双向策略。**测试**：跨租户用例零放行（CI Critical）+ 逐表策略验证 + 审计对账。

**框架层安全职责基线（补入职责封闭集合的第 10 项——原九项 + 安全基线）**：

| # | 职责 | 机制 |
|---|---|---|
| 10 | 安全基线 | ① 密钥管理：按租户数据密钥（DEK）+ 主密钥（KEK）两层，DEK 加密敏感字段，KEK 经 Vault/KMS；**轮转**：DEK 按版本字段（`key_version`）轮转，读时按版本解密、写时用当前版本，惰性重加密由后台任务批量推进；② 审计流自身治理（见下）；③ 备份与恢复演练：WAL PITR 恢复演练季度化，备份可恢复性验证进 CI |

**审计流自身治理**（审计全量不采样是信任承诺，但审计流本身即敏感行为画像，须防"审计员滥用"）：

1. **审计访问也要审计**（二级审计）：查审计流这一动作本身写入独立 append 流（谁查了谁的审计记录），两级流分离存储、分离权限；
2. **最小暴露**：审计查询默认聚合视图（按域/按时段），逐条明细查询需目标域明示授权或合规职务声明（声明入二级审计）；
3. **不可篡改**：月分区封存后加链式 hash（prev_hash 字段），防静默篡改；
4. **保留策略可配置但下限硬约束**：授权与跨域审计保留期下限写死为常量（法规底线），配置只能延长不能缩短。

**备份/导出按租户（A5 隔离矩阵补充项）**：导出文件默认加密（租户 DEK），导出动作入审计流；lite 档对应能力见《产品的技术选型》§六 lite 数据安全行。

## 九、无状态与扩容

| 部署单元 | 职责 | 扩容依据 |
|---|---|---|
| api | 同步读 + 受理 | RPS/连接数 |
| worker 池（cpu/gpu/llm 分池） | 执行节点 | 该节点队列深度（瓶颈单独扩） |
| scheduler | 就绪调度 + cron（leader 单活） | 低（主备） |
| push-hub | SSE/WS 扇出 | 连接数 |

全单元无本地状态 → K8s HPA 按队列深度扩缩 / Compose 手动扩；崩溃恢复 = 重领任务。**lite/minimal 档**：单实例（SQLite 单写者 + 内存锁/队列），图执行语义不变、并发 1-2；扩容路径 = 升级 full 档（数据经可携带层迁移）。
